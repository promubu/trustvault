# TrustVault Threat Model & Security Architecture

This document outlines the threat scenarios, assets at risk, attack paths, mitigations implemented, test verification evidence, and accepted gaps for the TrustVault application.

---

## 1. Assets at Risk

1. **Confidential Stored Documents**: Sensitive files (.pdf, .docx, .png, .jpg, .txt) stored in the server repository.
2. **Document Metadata & Titles**: Organizational information and search queries that could reveal sensitive business context.
3. **Audit Trail Integrity**: Cryptographic chain of custody recording authentication, uploads, downloads, edits, and access grants.
4. **User Identities & Authentication Credentials**: Argon2 password hashes and JWT bearer tokens.
5. **Authorization State**: Per-document grant mappings (`document_grants`) governing access privileges.

---

## 2. Threat Matrix

| Threat & Attack Scenario | Impact | Mitigation Implemented | Verification Evidence | Accepted Gap & Production Hardening |
|---|---|---|---|---|
| **Insecure Direct Object Reference (IDOR)**<br>Attacker enumerates or guesses document IDs (`GET /documents/{id}`) to access other users' files. | Unauthorized data disclosure. | Server-side authorization check `can_read()` evaluates ownership and explicit grants on every request. Unauthorized requests return `404 Not Found` rather than `403` to prevent ID enumeration. | `test_viewer_cannot_access_another_users_document`<br>`test_access_using_guessed_ids_returns_404` | External network firewalls and rate limiting on 404 responses to detect brute-force scanning. |
| **Revocation Bypass / Stale Session**<br>User whose access was revoked continues downloading files via pre-signed links or cached frontend state. | Continued access to confidential files after termination. | No permanent or pre-signed URLs are generated. The authenticated `/documents/{id}/download` endpoint re-evaluates database grants on every request. | `test_revocation_takes_effect_on_next_request` | Files already downloaded to local client storage prior to revocation cannot be recalled by the server. |
| **Vertical Privilege Escalation**<br>Unauthenticated or viewer user calls administrative or owner endpoints (e.g. attempting to upload, manage grants, or register as admin). | Unauthorized administrative control or unauthorized uploads. | Role enforcement in API dependencies (`current_user`). `POST /auth/register` hardcodes assigned role to `"viewer"`, ignoring client-submitted roles. | `test_user_registration_prevents_privilege_escalation`<br>`test_viewer_cannot_upload_documents`<br>`test_viewer_cannot_grant_or_revoke_permissions` | Fine-grained RBAC permissions matrix and admin multi-factor authentication (MFA). |
| **Horizontal Privilege Escalation**<br>User B attempts to edit, rename, delete, or share User A's document. | Tampering with or deleting other users' documents. | Ownership check (`doc.owner_id == user.id`) strictly required to grant/revoke access or delete documents. Edit permission requires explicit `edit` grant. | `test_viewer_with_read_permission_cannot_edit_or_delete`<br>`test_unauthorized_owner_cannot_grant_on_other_owners_document` | Version control / history of document edits with rollback support. |
| **Search Metadata Leakage**<br>Attacker uses search query parameters (`GET /documents?q=Confidential`) to discover the existence of unauthorized files. | Information disclosure of confidential document titles. | `GET /documents` enforces SQL-level filtering (`Document.owner_id == user.id OR Document.id IN (grants)`) before applying search filters. | `test_search_filtering_does_not_leak_unauthorized_documents` | Full-text search engine (e.g. PostgreSQL tsvector) with row-level security (RLS). |
| **Malicious File Upload / Content Spoofing**<br>Attacker uploads executable code disguised as `.pdf` or `.txt`. | Remote code execution, server compromise, or parser exploit. | Magic-byte signature verification (`validate_file_content`) inspects binary headers for `%PDF-`, PNG magic bytes, JPEG SOI markers, and DOCX ZIP signatures. Non-matching files are rejected with `400 Bad Request`. | `test_owner_upload_and_content_validation` | Antivirus / malware scanning pipeline (e.g. ClamAV sidecar) and sandbox execution. |
| **Resource Exhaustion / DoS via Upload**<br>Attacker streams an extremely large file to consume disk or memory. | Server disk saturation, denial of service. | Strict 10 MB streaming limit enforced during chunked read; exceeding files abort with `413 Payload Too Large` and remove partial files. | `test_oversized_upload_is_rejected` | Reverse proxy (e.g. Nginx `client_max_body_size`) limit before request hits application workers. |
| **Path Traversal / Filename Collision**<br>Attacker passes `../../etc/passwd` or collision names in upload or download. | Arbitrary file overwrite or system file disclosure. | Stored files use random cryptographically secure hex tokens (`secrets.token_hex(24) + suffix`). `safe_path()` verifies target path is strictly within `UPLOAD_DIR`. | `test_owner_can_delete_document_and_files`<br>Code inspection in `safe_path()` | Isolated S3-compatible object storage (e.g. AWS S3 or MinIO) with private bucket ACLs. |
| **Audit Log Tampering**<br>Attacker modifies audit events in the database to remove evidence of unauthorized access. | Repudiation and loss of forensic traceability. | Cryptographic SHA-256 hash chain linking every audit event to the previous event hash. `/audit/verify` re-calculates the chain and detects any modification, deletion, or reordering. | `test_audit_chain_detects_tampering`<br>`test_sequential_audit_events_maintain_valid_chain` | A privileged database administrator could recalculate the entire chain. Mitigation: stream audit events to external WORM (Write Once Read Many) storage. |
| **Sensitive Data Leakage in Audit Logs**<br>Passwords, bearer tokens, or document contents are logged in audit records. | Credential harvesting from audit trails. | Audit events record only metadata (`actor_id`, `document_id`, `action`, `outcome`, non-sensitive detail). Passwords and tokens are never passed to `write_audit`. | `test_audit_records_denied_and_allowed_actions_without_secret_leakage` | Automated PII / secret redaction filter on audit detail serialization. |
| **Token Theft / Session Hijacking**<br>Attacker intercepts or reuses JWT bearer tokens. | Account impersonation. | Short-lived signed JWTs (2 hours) using HS256 with long random secret. | `test_protected_endpoint_requires_login` | Use HTTP-only secure cookies with CSRF tokens, token revocation blocklist / Redis store, and HTTPS transport. |
